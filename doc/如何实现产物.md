先说结论：这个问题其实是**两个独立问题**叠在一起，得分别解决。

## 根因拆解

**问题一：文件写到了服务端机器上**

`write_file` 是 `HarnessAgent` 自动注册的平台工具。项目里 `ReActAgentConfig.harnessAgent(...)` 没有调 `.filesystem(...)`，所以走的是默认分支（`HarnessAgentBuilderSupport` L165-167）：

```java
// Default: route through LocalFilesystemSpec so the default project (= ${user.dir})
return new LocalFilesystemSpec().toFilesystem(workspace, nsFactory);
```

而 `LocalFilesystemSpec` 的默认值是：
- `project = System.getProperty("user.dir")` → 在 IDEA 里跑就是仓库根目录 `D:\...\spring-ai-study`
- `mode = LocalFsMode.ROOTED`，`PathPolicy = [project, workspace, additionalRoots]`

所以模型给一个**落在项目根目录下的绝对路径**时，策略判定为"允许"，文件就 literally 写进了服务端的项目目录。这不是 bug，是默认配置的语义。

**问题二：就算在磁盘上，也没有交付通道**

项目目前唯一的产物链路是 `FileGenMiddleware` → `./output/conversation_{messageId}.md` → `m_chat_message_file` → `/file/download?messageId=`。而平台工具 `write_file` 完全绕过这条链路，模型只能在正文里贴一个路径字符串 —— 对发起请求的浏览器用户来说毫无意义。

所以：**既要收口"写哪儿"，也要建"怎么交付"**。

## 可选方案

### A. 内容直出（零后端改动，最轻）

Prompt 里禁止写文件，要求把 HTML 全文放在回答里；前端把代码块渲染成「预览 / 下载」按钮，用 `Blob + URL.createObjectURL` 在浏览器本地生成文件，HTML 游戏还能直接 `<iframe srcdoc>` 玩。

- ✅ 天然多用户隔离、可预览、改动全在前端
- ❌ 只适合单文件小产物；多文件/二进制/大文件不行，吃 token

### B. 官方 `deliver_artifact` 通道（推荐）

`HarnessAgent.Builder.artifactDeliveryTarget(...)` 一旦设置，框架会自动注册 `deliver_artifact` 工具，并在 system prompt 里要求模型"产出文件后主动投递，且不要在回复里啰嗦这件事"（见 `ArtifactDeliveryTool` 的 `@Tool` description）。

我需要实现的就是那个 `@FunctionalInterface`：

```java
public interface ArtifactDeliveryTarget {
    ArtifactDeliveryResult deliver(RuntimeContext rc, ArtifactDeliveryRequest request);
}
// request: filePath / byte[] content / fileName / description / force
// 返回: ArtifactDeliveryResult.success(msg) / fail(err) / conflict(err)
```

实现里做三件事：① 把 `content` 落到**共享存储**（OSS/MinIO，或先落一个挂载的共享目录）；② 插一行 `m_chat_message_file`（存 objectKey，不存绝对路径）；③ 让前端拿到 FILE 事件出下载卡片。

- ✅ 框架正解，`fileName` 已由工具校验过无路径穿越；无需改模型行为就能把产物送到用户手里
- ⚠️ 两个注意点：`artifactDeliveryEnabled = artifactDeliveryTarget != null && !disableFilesystemTools`（不能禁用文件工具）；当前 FILE 事件只在 `FileGenMiddleware` 的 `concatWith` 里发，走 B 需要在 `toStreamEvent` 里识别 `deliver_artifact` 的 `ToolResultEndEvent`，或让 target 自己发 `CustomEvent`

### C. 收口写入位置（和 B 配套，防事故）

```java
.filesystem(new LocalFilesystemSpec()
        .mode(LocalFsMode.SANDBOXED)      // 拒绝工作区外的绝对路径
        .projectWritable(false)           // 非工作区写入不进项目树
        .project(Path.of(sharedUploadDir)))
.workspace(perUserWorkspaceRoot)          // 配合 IsolationScope.USER/SESSION 命名空间
```

- `IsolationScope` 可选 `USER`（默认）/`SESSION`/`AGENT`/`GLOBAL`，决定文件命名空间隔离粒度 —— 你仓库里 `.agentscope/workspace/1001/...` 就是 USER 命名空间的产物
- 更激进：`.disableFilesystemTools()`，工具清单里直接没有 `write_file`。但会连带失去 `read_file`，功能面收窄（这也是记忆里那条"DENY 规则 vs Builder 开关"取舍的同类问题）

### D. 换存储后端（多副本部署时必需）

| 方式 | 说明 | 代价 |
|---|---|---|
| `.filesystem(new RemoteFilesystemSpec(baseStore))` | 工作区文件落到 KV store（自己实现 `BaseStore`，背后是 OSS/Redis/MySQL）；`deliver_artifact` 从这里 `downloadFiles` 取字节 | **没有 shell**（`execute` 不可用） |
| `SandboxFilesystemSpec` + `DockerSandbox` | 每会话一个容器，文件彻底隔离在容器内，安全边界最好 | 运维最重，需 snapshot spec 跨请求恢复 |

### E. 顺手要修的两个既有缺陷（无论选哪个方案）

1. `FileGenMiddleware` 往 `m_chat_message_file.file_url` 存的是 `filePath.toAbsolutePath()`，`FileController` 用 `Files.exists` + `FileSystemResource` 读本机盘 —— 多节点/容器化后必然 404。应改成相对 key。
2. `FileController.downloadByMessageId(messageId)` 只按 messageId 查，**没有校验这条记录属于当前登录用户**（`getByMessageId` 无 userId 条件）—— 越权下载。加 userId 过滤。

## 按场景推荐

- **就是本机自娱自乐**：A 或 C 单用，够了
- **当前项目定位（多用户 Web 应用，单机部署）**：**B + C + E** —— `deliver_artifact` 落本地共享目录 + `SANDBOXED` 收口写入 + 修下载链路。后续要扩容就把存储换成 OSS
- **多副本生产**：B + C + E + D（`RemoteFilesystemSpec` 或 Sandbox）

## 零成本止血（可以今天就改）

在 `sysPrompt` 里加一句："不要将文件写入服务器本地路径；需要产出文件时调用 `deliver_artifact`（若可用），否则把完整内容直接放在回答中。" 能立刻消除"贴个 D:\ 路径给用户"这种体验，但正式方案还是得靠 B。
